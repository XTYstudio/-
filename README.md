# 数据分析与 AI 数据岗位技能观察

这是一个基于公开招聘信息的小型、可复查分析项目。目标是展示我如何收集岗位样本、把招聘原文转换成可统计字段、抽查并修正规则，再把结果做成可筛选的静态看板。它是一个可解释的分析原型，不代表全市场调查，也不是自动爬虫或自主 Agent。

## 研究问题

在本项目选出的中国大陆公开岗位中，哪些数据分析、商业分析、数据产品和 AI 数据工作流技能被明确提到？不同类型岗位有什么差别？新增岗位进入样本后，数据表和看板能否按同一流程更新？

## 样本与口径

- 截止快照：2026-11-12；共 **26 条岗位记录、8 家公司**（Apple 4、美团 7、小红书 4、腾讯 3、阿里巴巴 2、字节跳动 2、Amazon 2、华为 2）。地区主要为中国大陆，具体地点见岗位表。
- 这是按相关性选择的目的性样本，不是随机样本；岗位类型、经验级别、招聘批次和公司分布不均。结论只描述这 26 条记录，不能推断整个市场，也不专指应届岗位。
- `date_posted` 只填页面明确给出的发布日期；未标明时写“发布日期未标注”。页面更新时间、校园招聘批次或本次首次核验日期另记在 `page_updated_or_first_seen`，不能把它们冒充发布日期。
- 每条岗位都记录岗位类型、地点、经验要求、来源类型、链接和状态备注。官方来源与第三方汇总分开标识；第三方岗位和只有官方索引/列表的项目需要打开原页进一步核对。招聘信息可能过期，使用时应重开链接。
- 技能计数单位是“岗位”。同一岗位的同一规范技能只计一次；一个岗位可贡献多个技能。技能覆盖率 = 提到该技能的不同岗位数 ÷ 当前岗位数。当前无筛选时分母为 26；例如 SQL 是 17/26（约 65%）。按四舍五入显示百分比。不同技能可能同时出现在同一岗位，因此各项比例相加可以超过 100%。
- `skills.csv` / `evidence.csv` 当前有 **292 行技能证据**；这是岗位-技能配对数，不是岗位数。当前共 155 个规范标签。Apple Ads 第一条岗位经用户提供原文截图复核后，补录了 14 项技能/能力证据；因此早期更新流程演示时记录的 88 行是当时的历史值，不是当前最终值。看板技能条形图按岗位去重计数，而不是按证据行数计数。
- “必需 / 优先 / 描述不清”只根据文本中清楚的 Minimum、Required、Preferred 等上下文规则初判。若页面没有清晰区块，保持“描述不清（需回原文确认）”；不能把“没看到必需”解释成“不要求”。

## 数据来源与人工核查

来源链接和原文短证据保存在 `data/postings.csv`、`data/evidence.csv`。我对代表性岗位原文做了抽查，并把发现、修正及词典规则写进 `data/audit_log.csv`。最近根据用户提供的 Apple Ads 岗位原文截图，发现首条岗位原先只列少量技能，已补充技能、上下文摘录及审核状态；发布日期改为未标注。先核对主表第 2–10 条（3 条 Apple、6 条美团），补齐技能、移除未获来源支持的 SQL 标签并保留经验要求冲突；本轮继续核对剩余 16 条，覆盖腾讯、小红书、阿里、字节、Amazon、华为和一条美团岗位，补齐遗漏、修正来源及必需/优先级别。岗位、技能、证据和审计表已同步更新。例如，小红书 AI 数据分析岗位首轮规则漏掉产品规划和评测框架；小红书数据引擎岗位漏掉治理与异常检测；这些都补进规则并重新生成了技能表。美团一个 Agent 评测岗位的职位概览和资格正文对经验年限有冲突，所以保留两种说法并标为待核实，没有擅自选择一个数字。新增的补贴策略分析师岗位也有页头“2年”与资格正文“3年以上”的冲突，另在审计时发现并修正过一次标题与职位 ID 不匹配；这两类问题都记录在审计表中。

截至本轮，26 条岗位均已完成一次来源与技能标签核对；但证据强度不同：有的可直接读取雇主官网全文，有的只读到官方搜索索引，有的详情来自第三方收录页。每条的来源限制写在 postings.csv 的 review_status 和 audit_log.csv 中。所有 26 条均有人工核对记录，但没有第二位标注者进行独立复核。技能摘录通常是短语而非整段招聘文案，仍需点击来源检查上下文。来源页缺失或第三方来源需进一步确认的项目在记录中标明。

## 文件

- `index.html`：独立静态看板，可按公司、城市和岗位类型筛选；含岗位明细和逐条技能证据。
- `data/postings.csv`：26 条岗位主表，含来源和统计所需字段。
- `data/skills.csv`：规则提取出的岗位-技能标签。
- `data/evidence.csv`：技能证据表（当前与 skills 同源导出），可从短摘和链接回查。
- `data/audit_log.csv`：原文抽查、误漏项、修正规则及处理理由。
- `data/new_postings_template.csv`：新增岗位空白模板；字段和 `new_postings.csv` 一致。 主表另有 `review_status` 列，用于逐条记录人工复核进度。
- `data/new_postings.csv`：本次实际追加的美团商业分析师岗位样本。
- `scripts/update_dashboard.py`：本地规则匹配、去重、导出和看板重建脚本。

## 更新流程与本次结果

1. 复制 `data/new_postings_template.csv`，填写岗位字段；用唯一 `job_id`，保留来源网址和原文短摘。日期不明就写“发布日期未标注”。
2. 将新增行放入 `data/new_postings.csv`，然后在项目目录运行：

   ```bash
   python3 scripts/update_dashboard.py
   ```

3. 脚本将未见过的 ID 加入主表，对新岗位执行关键词初筛，再写出技能证据并重建 `index.html`。重复 ID 会跳过。
4. 打开来源原文，检查误报、漏报、类别及要求级别。发现系统性漏项时更新 `scripts/update_dashboard.py` 的词典，把例子和规则记进 `data/audit_log.csv`，再重跑。不要只看脚本输出就把标签当成事实。

新增美团岗位（jobUnionId 4600837267）曾通过脚本验证增量去重：首次新增 1 条，岗位总数达到 26；重复运行新增 0 条。之后依据 Apple Ads 原文补齐技能证据，并完成 26 条岗位的来源与技能复核记录；当前数据为 26 条岗位、292 行技能证据、155 个规范标签。

## 当前观察（仅限这批样本）

按“包含该规范技能的不同岗位数 / 26”计算：

| 技能 | 岗位数 | 覆盖率 |
|---|---:|---:|
| 数据分析 | 18/26 | 69% |
| SQL | 17/26 | 65% |
| 沟通与跨团队协作 | 15/26 | 58% |
| 指标设计与监控 | 14/26 | 54% |
| AI工具使用 | 8/26 | 31% |
| BI与数据可视化 | 7/26 | 27% |
| 大数据技术 | 7/26 | 27% |

这些数字表示所收集的岗位描述提到该标签的次数（按岗位去重），不是实际工作中技能的重要程度或雇主真实优先级。`Python` 与 `Python/R` 是不同文本口径：后者对应岗位明确接受 Python 或 R 的表述，不应相加后说成 12 个岗位具备 Python 要求。

## 工具和分工

我用 Codex 中的 `job-skill-analyzer` Skill 帮助按一致格式整理岗位证据和技能；我本人负责确定纳入范围、检查来源与字段、抽查分类、决定如何处理冲突、修正规则并解释结果。Python 标准库脚本负责可重复的关键词初筛、岗位 ID 去重、CSV 输出和 HTML 看板生成。看板本身是离线静态 HTML。

Skill 提供分析指引，不会自动抓网页；本地脚本也不联网。所谓“自动处理新增岗位”在此项目中的准确含义是：人工提供新岗位行后，脚本自动去重、按有限词典初筛并刷新统计和看板。它尚未实现招聘网站抓取、计划任务、邮件提醒、动态数据库或完全自主 Agent。

## 局限与下一步

1. 样本小且目的性选取，部分来源为第三方或列表页；发布状态和日期可能变化。
2. 关键词规则可能漏掉同义表达，也可能在特殊语境下误报；短摘可能丢失上下文。技能分类和必需/优先判断仍须人工复核。
3. 技能词典是项目定义，不是标准行业 taxonomy；不同标签粒度不完全一致。当前统计没有按校招/社招或岗位类型分层后再作正式推断。
4. 下一步可以先把每个标签的边界定义成小型数据字典，对全 26 条逐条复核并记录复核状态；再扩大到 50–100 条，均衡公司和岗位类型；最后按季度保存快照，比较时间变化。若要称为 Agent，需要另行实现并验证网页发现、来源校验、异常处理和人工审批环节。

## 面试时可以这样介绍

> 我做了一个公开岗位技能观察原型，收集并整理 8 家公司的 26 条数据分析、商业分析、数据产品和 AI 数据相关岗位，保留来源、日期、岗位类型和经验要求。我用 Python 写了一个可重复的更新流程，把新岗位按固定词典初筛、去重并刷新静态看板；随后核查原文，发现 AI 产品规划、评测框架、数据治理和异常检测等标签漏项，于是修正规则并记录审计案例。SQL 在这批目的性样本中出现于 17/26 条岗位描述。样本不是随机抽样，脚本不是爬虫或自主 Agent，所以我只把它作为可解释的流程原型。下一步是扩大样本并逐条复核。

面试前应能现场解释：样本如何选、为什么分母是 26、17 个 SQL 岗位怎样逐条确认、哪些来源还待复核、规则在哪里可能出错，以及新增一条记录后脚本如何避免重复。只要能诚实讲清这些取舍，这个项目才是可讨论的经历；单纯把文件上传 GitHub 本身不构成项目经验。
